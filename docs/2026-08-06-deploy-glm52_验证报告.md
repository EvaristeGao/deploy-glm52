## 4. 发现并修复的 3 个实机 bug

提交 `fd4843f`：

### 4.1 Bug1：`--pid=host` 下 pkill 误杀 ssh
- **现象**：容器内 `pkill -f mooncake_master` 触发 `Connection reset`，ssh 会话被杀
- **根因**：容器 `PidMode=host`，容器内 pkill 看到 host 全部进程，`-f` 匹配到控制机 ssh 自身命令行
- **修复**：mooncake 用 `pkill -x mooncake_master`；proxy 用 `pkill -f '^python3 .*load_balance_proxy_server_example'`（锚定 cmdline 开头）。覆盖 start_mooncake_master / start_proxy / cmd_stop

### 4.2 Bug2：proxy 脚本来源
- **出入**：文档/deploy.sh 按「镜像内置」实现，实际是**手动提供的 Python 脚本**（内容在 a2.md，与同事实机逐字一致）
- **修复**：随附 `load_balance_proxy_server_example.py` 进项目根目录，`start_proxy` 自动 scp→docker cp 进容器 `/root/pd/` 后拉起，`script_path` 优先 config。不再依赖镜像

### 4.3 Bug3：proxy 就绪超时 120s
- **风险**：proxy `import vllm/torch` 冷启动慢，120s 可能不够
- **修复**：`runtime.proxy_ready_timeout` 默认 600s，保留「引擎全部就绪后再起 proxy」顺序

**附带**：日志路径可配（config `logs` 段）。

## 9. mooncake 缓存验证

**问题**：mooncake Admin Metrics 采样显示 `Keys: 0`、`Mem Storage: 0 B`，即使跑了请求。

**结论：缓存正常工作**，证据在 vllm 日志：
- **prefill**（p0）：`mooncake_connector.py[1851] Delaying free of blocks`（KV 存入 mooncake 等 decode 拉）
- **decode**（d0）：`mooncake_connector.py[948] KV cache transfer ... took 63ms`（从 prefill 拉 KV，remote_session 指向 p1）

**原因**：KV 是**瞬时流式传输**（prefill 写→decode 毫秒级拉→释放，63ms），而 mooncake 指标每 10 秒采样，采样时刻 KV 已消费。判断缓存是否工作看 vllm 日志的 `KV cache transfer`，而非 Mem Storage 采样。
