# 高并发、长输入 P/D 性能对照

2026-11-08，18组正式测试完成，**1440/1440请求成功**。三档同一GLM-5.2
W4A8C8权重；每点N80、0% P侧跨请求前缀命中。vLLM生产代码和默认inventory未改。

## 结论

30提高到40并发，本轮三档均未出现请求失败、抢占或吞吐断崖。
kvoffload吞吐变化为55K -3.1%、96K +3.7%、128K +3.5%，TPOT变化在
-6.7%到+6.0%之间；TTFT P50却增加37%–71%，主要表现为饱和后的排队放大。
DCP吞吐基本完全持平，TTFT也增加41%–61%。原始档吞吐增加8%–11%，
TPOT增加4%–14%。这些是单轮有限批次结果，不是生产SLO容量保证。

与DCP相比，kvoffload在55K吞吐更高，96K基本接近，**128K出现明确差距**：
C30/C40 TTFT P50分别高39.5%/35.8%，输出吞吐低15.2%/12.2%。这不是40并发
突然崩溃；相同2K输出下，从96K到128K，kvoffload吞吐下降约36%，DCP约23%。
P侧长上下文路径是下一步优先定位对象。

原始INT8档TTFT最低，但D生成较慢，TPOT约157–180ms，整轮吞吐最低。
不要只按TTFT排序：闭环负载中较慢的D会延后新请求到达P，后续请求的P队列反而
更短。相反，128K下kvoffload约28ms的TPOT也包含D供给不足的影响。

96K→128K、输出同为2K时，kvoffload P平均prefill增加约56%–58%，DCP约32%–33%，
而输入仅增加33%。kvoffload在128K的P平均prefill约48s，DCP约17s；P副本数
分别为4和2，不能把单请求时长之比直接当成总prefill吞吐之比。kvoffload的P
平均排队达到141/173s，D running峰值仅8/10，低于本档4×8的decode序列上限。
因此目前更直接的证据是P供给不足，而非D decode序列已经跑满。

只读检查实际P的vLLM scheduler源码：长请求贪心消耗token_budget，默认
long_prefill_token_threshold=0。本档每步16384 token，seq8不代表8条长prefill
同时推进，采样每P多数只有1–2条running。简单增加seq未必有效；切小chunk也
会增加逐层历史恢复次数。没有采集算子/搬运timeline，尚不能把差距定量归给
具体Store GET、恢复拷贝或DSA算子。本轮不调整配置或做优化，以保持矩阵一致。

kvoffload在128K/C40的D KV块池采样峰值为98.6%，容量余量值得关注。
该指标不是物理HBM或Host DRAM占用百分比。当前Host仍100GiB/DP，未扩为1TB。
D-first预登记使D等待和占用时点包含等待P；原版两档P-first在P完成后才进入D。
不能把P/D排队时间相加解释TTFT，也不能按KV百分比直接比较三档物理容量。
本轮完成不代表更高并发或更长输入仍安全。
